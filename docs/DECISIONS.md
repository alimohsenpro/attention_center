# Decisions

Decisions taken by the product owner during discovery (2026-11-09). They are settled: do not
reopen them in code. If one blocks a task, escalate.

## Product

| ID | Decision | Reason |
|---|---|---|
| D-01 | The product is a unified attention center with pluggable sources, not an enhanced bell and not a full work inbox | Approvals and unit queues never create bell notifications; a full inbox would duplicate the source apps |
| D-02 | The window opens automatically after login only when the user has action items, once per login session | A window that always opens is closed unread within weeks |
| D-03 | A periodic reminder repeats every N hours while urgent, immediate or overdue items exist. It is a small toast with a tone, and never opens the window by itself | A window that opens over someone typing steals keystrokes and gets dismissed |
| D-04 | Sound by default only for action items, with distinct organisation tones for urgent and immediate. The user chooses one of three scopes: urgent only / action items / everything | Sound loses its value when everything makes a sound; the user asked to keep "everything" as an opt-in |
| D-05 | The default display mode is a centred dialog with tabs and a paginated table. A panel above the launcher and a side drawer are alternative modes. The admin sets the default; the user may change it | Owner's preference, with choice left to each user |
| D-06 | The user controls sound, tone, volume, scope, Do Not Disturb, auto-open and display mode, but cannot hide the counter or the visual signals for urgent, immediate and overdue items | Urgent work must not become invisible |
| D-07 | Announcements are a simple, targeted system announcement with optional acknowledgement and a list of who acknowledged, in release 0.2. Official circulars stay in the correspondence app and arrive through a source | Avoid duplicating an existing circular workflow |
| D-08 | The window opens documents; it does not approve, refer or reply | Acting without opening the document is a governance risk; each app owns its actions |
| D-09 | OS-level (browser) notifications are a future feature | The reference deployment runs on plain HTTP, where browsers block them |
| D-10 | Tones are short, non-melodic and professional, suited to operations work (incoming item, urgent, immediate, reminder). They are generated by a script in the repository. The owner listened to the generated set and approved it on 2026-11-09; do not change the tones without a new decision | Formal workplace; no third-party audio rights |
| D-11 | Name: Attention Center, package `attention_center`. The window title is "What needs your attention" / «ما يحتاج انتباهك» | |
| D-12 | The default visual identity follows `docs/DESIGN_TOKENS.md`: deep green with gold accents, calm surfaces, a four-step priority colour scale | Owner's request; expressed as neutral tokens, with no logo or organisation name |
| D-13 | All consumer apps are Frappe apps on the same site. No cross-site or REST ingestion in 0.x | Confirmed by the owner |
| D-14 | Frappe's bell and theme bells are left alone. An optional setting hides the stock bell by CSS | Themes replace the bell; Frappe 16 moves it |

## Engineering

| ID | Decision | Reason |
|---|---|---|
| T-01 | Sources are federated: items are computed live from the source app; nothing is copied | One system of record; permissions and field masking stay with the source |
| T-02 | Two source types: declarative DocType query (hook or admin-defined) and Python callables (hook only) | Covers ERPNext-style DocTypes without code, and unit queues or Python-only "waiting on me" logic with code |
| T-03 | A consumer app declares sources as plain data in its `hooks.py` and never imports this app | The consumer keeps working when Attention Center is not installed |
| T-04 | The client renders in a Shadow DOM host appended to `document.body`, at the bottom inline-end corner | Desk themes replace the navbar and ship aggressive global CSS; their sidebars occupy the inline-start side |
| T-05 | Realtime nudges are content-free and sent after commit; the client also refreshes on visibility, reconnect and a slow heartbeat | Frappe's socket gives up after three failed reconnects; payloads must not leak data |
| T-06 | Cross-tab coordination uses BroadcastChannel and localStorage only | The Web Locks, Notification and Service Worker APIs need a secure context |
| T-07 | Counts are capped at 99 and computed from one capped query per source, cached per user for a short TTL | Cheap, permission-aware, and identical on Frappe 15 and 16 |
| T-08 | The approvals source checks read permission per document | `Workflow Action` is filtered by role only |
| T-09 | No UI framework; vanilla ES modules bundled by Frappe's esbuild | Small bundle, no dependency, testable pure logic |
| T-10 | Tests: `FrappeTestCase` for the backend, `node --test` for pure client logic, a small Playwright smoke suite from M6 | |
| T-11 | The pipeline merges automatically only when CI is green and the independent reviewer agent approved the exact commit. The coordinator enforces both and verifies `main` after every run; GitHub branch protection with the two required checks is recommended on top but not assumed | Owner asked for uninterrupted delivery with gates |

## Open points for the owner

- Which desk theme runs in production? Compatibility with the stock desk is tested by the pipeline; theme compatibility must be checked on the owner's bench.
- Default reminder interval is 2 hours until the owner says otherwise.

## Agent decisions

Add one line per decision: `YYYY-MM-DD — task — decision — why`.

- 2026-11-10 — M0-T1 — `bench_up.sh` builds Frappe's own assets when they are missing (11–12 s) — without them `/login` and the desk answer HTTP 500, so the sandbox bench could not be opened in a browser.
- 2026-11-10 — M0-T1 — `bench_up.sh` recreates an incomplete `test_site` with `--force` but never deletes an incomplete bench directory; it stops with a message instead — the site is the script's own throwaway, while `BENCH_DIR` may point at a developer's real bench.
- 2026-11-10 — M1-T1 — `Attention User Preference.volume` is a Data field holding "" or a whole number 0–100 — Frappe creates Int columns as NOT NULL, so "empty = use the default" could not be stored and a lazily created preference would silence the user.
- 2026-11-10 — M1-T1 — only a save flagged `doc.flags.from_hooks` may set `is_system` or `app` or change a system source's definition, and non-system sources cannot name callables — read-only fields are not enforced on the server, and Python sources must come from hooks only (NFR-SEC-02).
- 2026-11-10 — M1-T1 — `after_migrate` stores missing settings defaults and `after_install` stays unwired until M1-T2 needs it — Frappe already stores a Single's defaults at install (`init_singles`) and creates the role from the DocType permissions and the fixture, but never fills a field added by an upgrade.
- 2026-11-10 — M1-T1 — DocType words that Frappe also translates (`Enabled`, `Label`, `Action`, `User`, …) get their Arabic in `ar.csv` with the DocType name as context (third column), and server messages translate field labels with the same context — Frappe translates form labels, descriptions and Select options with the DocType as context and falls back to the plain string, so the app's wording applies in its own forms without changing Frappe's anywhere else; `test_translations.py` enforces it.
- 2026-11-10 — M1-T1 — `in` / `not in` filter values must be JSON lists; a comma-separated string is rejected — one form per operator is what §3.2 documents and keeps placeholder handling in the query engine simple.
- 2026-11-10 — M1-T2 — `Attention Source.hook_label` (hidden, read-only) keeps the label last declared in the hooks, and the sync relabels a system source only while `label` still equals it — §4.6 keeps an admin's label but should follow the app's otherwise, and nothing else records which of the two the stored label is.
- 2026-11-10 — M1-T2 — targeting by roles and user groups is a union: any listed role or any listed group admits the user — admins list an audience ("these roles and this team"); requiring both would hide the source from people they named.
- 2026-11-10 — M1-T2 — a hook entry with a key its type does not define is rejected, not ignored — a misspelt `filter` would otherwise be dropped silently and widen the query.
- 2026-11-10 — M1-T2 — the contract checks the shape of a hook entry and the `Attention Source` controller checks its filters, priority map and fieldnames when the sync saves it — one set of rules for desk and hook sources.
- 2026-11-10 — M1-T2 — a system source disabled because its entry vanished or became invalid stays disabled when the entry comes back — the sync cannot tell its own disabling from an admin's, and staying hidden is the safe side.
- 2026-11-10 — M1-T2 — a hook entry whose key is already used by a source created in the desk is skipped and logged, and the desk source is left as it is — an admin's definition and targeting are not overwritten silently; deleting the desk source lets the app's entry in at the next migrate.
- 2026-11-10 — M1-T2 — an item with an invalid optional value (priority, colour, label, date) is kept with the default; only id, title and route are required — dropping it would hide work the user can still open.
- 2026-11-10 — M1-T2 — a `due` date without a time is overdue from the next day on — a task due today is not late yet.
- 2026-11-10 — M1-T2 — rejected hook entries are logged at ERROR, dropped items at WARNING as §4.3 says — Frappe's default production log level is ERROR, so a warning about a skipped source would never reach the operator.
- 2026-11-10 — M1-T2 — a hook entry whose filters or priority map hold a value JSON cannot store (a `date`, a `set`) is rejected, not converted — the stored definition is JSON, and a guessed conversion (date format, set order) could change what the query matches; rejection logs and skips it like any other bad entry.
- 2026-11-10 — M1-T2 — `ContractError` messages are written to the log only and are not translated — they address the developer of the declaring app; a later task that shows one to a user must wrap it with `_()` first.
- 2026-11-10 — M1-T3 — a declarative source's `new_since` counts every row when the user has no watermark for it yet — the user has seen none of them, and the login line (§7.4) should say so.
- 2026-11-10 — M1-T3 — the count cache keeps failed results for the TTL like successful ones — a broken or slow source would otherwise run (and wait for its timeout) on every summary of every user.
- 2026-11-10 — M1-T3 — declarative queries get a 2 s statement timeout, the same budget after which any source is logged as slow — NFR-PERF-03 asks for one time budget, and 2 s is far above a capped query on 10 000 rows.
- 2026-11-10 — M1-T3 — the timeout uses `frappe.db.set_execution_timeout` and restores `get_query_execution_timeout()`, not `frappe.db.execution_timeout()` — the design names the former (read from Frappe 15.91), while the context manager was only confirmed in 15.126 and the app supports every 15.x.
- 2026-11-10 — M1-T3 — a slow source is logged at WARNING, a failed one at ERROR — slowness is a performance hint an operator looks for when lowering the log level; a failure shows to users and must reach the default production log.
- 2026-11-10 — M1-T3 — the runner drops the messages a failed source queued with `frappe.msgprint`/`frappe.throw` — Frappe sends them to the browser with the response, so a broken source would open an error dialog on every background refresh.
- 2026-11-10 — M1-T3 — a python source's count of the wrong shape (text, negative, bool, bad `latest`) fails the source instead of falling back to 0 — a wrong count has no harmless default, unlike an item's optional label.
- 2026-11-10 — M1-T4 — `route_fields` also takes a `route` key (a field holding a desk route), stored with `doctype` and `name` in three Data fields of Attention Source — Notification Log's `link` must win over its reference document (§4.5), and Data fields get the same "field exists" check and desk form as the other mapped fields.
- 2026-11-10 — M1-T4 — the approvals title is the title field only when the user may read its permission level, otherwise the document name — field masking stays with the source app (T-01).
- 2026-11-10 — M1-T4 — an open Workflow Action whose document or DocType is gone is skipped instead of failing the approvals source — Frappe leaves actions behind when a DocType is deleted, and one stale row must not hide every other approval.
- 2026-11-10 — M1-T4 — the approvals hook entry declares no `get_recipients`; the role holders are left to `engine/recipients.py` (M2-T1) as §6 describes — the python contract returns a plain list of users and cannot ask for the broadcast needed above 200 recipients.
- 2026-11-10 — M1-T4 — "view all" routes are `/app/workflow-action?status=Open`, `/app/todo?status=Open` and `/app/notification-log?read=0` — a route cannot name the session user; Frappe's own list permissions limit the first two to the user's actions and ToDos, except for System Managers, who see every open ToDo.
- 2026-11-10 — M1-T4 — Arabic labels of the built-in sources that Frappe already translates (`Assignments`, `Notifications`) carry the `Attention Source` context in `ar.csv` — the app's wording («التكليفات», «الإشعارات») then applies where labels are translated with that context, without changing Frappe's wording elsewhere.
- 2026-11-10 — M1-T5 — the endpoints and the boot require `user_type` System User, so website users are refused like Guest — a source without targeting is meant for every desk user (§4.6), and a website user is not one.
- 2026-11-10 — M1-T5 — `get_items` also returns the `state` of the run — a failed items call shows nowhere else, and FR-UI-02 asks for an error state per tab.
- 2026-11-10 — M1-T5 — a hidden source and a missing key get the same `PermissionError` message — the error does not tell a user which sources exist.
- 2026-11-10 — M1-T5 — `set_preferences` rejects unknown names instead of ignoring them — watermarks and the auto-open session hash live in the same row and are not the client's to write, and a rejected name shows a client bug at once.
- 2026-11-10 — M1-T5 — preference values are the DocType's own options (`Dialog`, `Urgent Only`, `Default`, `""` to inherit) in the API too — one vocabulary for storage, API and form, with no mapping layer.
- 2026-11-10 — M1-T5 — a user's `tone` must be a `standard` tone of `tones.json` — FR-SND-01 makes the urgent, immediate and reminder tones the organisation's, and FR-SND-02 lets the user pick a standard tone.
- 2026-11-10 — M1-T5 — `test_source` checks the two manager roles itself instead of calling `frappe.only_for` — `only_for` returns at once while tests run, so no test could prove the check.
- 2026-11-10 — M1-T5 — `test_source` runs disabled sources too and drops the caller's cached count first — a manager tests a definition before enabling it or right after changing it; the run still uses only the manager's own permissions.
- 2026-11-10 — M2-T1 — the watch map is kept in `frappe.cache` (request-local copy, 5-minute expiry, cleared with the visibility cache) instead of a per-process map — a per-process map cannot be cleared in the other workers when a source changes, and the request-local copy still keeps an unwatched DocType at one dict lookup and no query.
- 2026-11-10 — M2-T1 — the approvals hook entry declares `watch_doctypes: ["Workflow Action"]` — the watch map stays the same rule for every source and the source form shows what it watches; `engine/recipients.py` still computes the role holders.
- 2026-11-10 — M2-T1 — an audience that cannot be listed is broadcast: a declarative source without recipient fields, a python source without `get_recipients` or whose `get_recipients` fails or returns no list, and an action open to `All`, `Desk User` or `Guest` — §6's rule for an unknown audience; a nudge carries no content, and skipping it would leave counts stale until the next refresh.
- 2026-11-10 — M2-T1 — the audience cap of 200 applies to every source and to `nudge()`, and only enabled users count as holders of a role — one rule for every audience; disabled users have no session to nudge and would push a role over the cap for nothing.
- 2026-11-10 — M2-T1 — a broadcast names no actor, and a source broadcast in a transaction is left out of that transaction's user nudges — every desk user receives a broadcast and need not learn who acted; a user nudge for the same source would only repeat it.
- 2026-11-10 — M2-T1 — `nudge()` raises a translated `frappe.ValidationError` for a key that names no source and for users that are not a list of user ids, and accepts a disabled source — a wrong key is the consumer developer's bug and should show at once; a disabled source is an admin's choice and must not break the consumer's job.
- 2026-11-10 — M2-T1 — the document-event handler and the after-commit callback catch every exception and log only the DocType and the exception type — a failure in this app must never stop a user's save, and after the commit an exception would reach a request whose changes are already saved.
- 2026-11-10 — M2-T1 — approvals watch the DocTypes of the active workflows and, on a transition or a deletion, nudge the holders of the roles allowed out of the state the document leaves, read from the Workflow definition without evaluating transition conditions — Frappe completes and deletes the actions with queries before this app's handler runs; a larger content-free audience costs a refetch, a smaller one leaves a stale count.
- 2026-11-10 — M2-T1 — a save that keeps the workflow state nudges no approver from the document — Frappe changes no action then, and every edit of a document under a workflow would otherwise nudge all its approvers.
- 2026-11-10 — M2-T1 — the watch map is cleared on `Workflow` `on_change` and `after_delete` (not `on_trash`) — in `on_trash` the row still exists and the `*` handler that runs right after would cache the deleted workflow again.
- 2026-11-10 — M3-T1 — a root `package.json` that only declares `"type": "module"` (no dependencies, no scripts) — Node 18 in CI loads the client's `.js` ES modules for `node --test` only when a package declares them modules; the `yarn install` bench runs on it installs nothing.
- 2026-11-10 — M3-T1 — the collapse control is a small separate button beside the launcher, always visible, whose label says what it does ("Collapse the launcher" / "Expand the launcher") — a control shown only on hover cannot be found by keyboard or touch, and the launcher's own click stays for opening the window.
- 2026-11-10 — M3-T1 — the tab title shows the launcher's count text, `(99+)` included, and removes only the prefix the app wrote — one number in both places, and a page title that starts with a number in brackets is not eaten.
- 2026-11-10 — M3-T1 — the title counter is kept by a `MutationObserver` on `<title>` alone, without a `frappe.router` listener — the observer sees every title Frappe writes, navigation included; a route change that writes no title leaves the prefix in place.
- 2026-11-10 — M3-T1 — an exception anywhere in the client turns it off for the page load and undoes what it added (host, observers, title counter), while a failed request only leaves the launcher as it was — NFR-REL-01 asks for disabling on failure; a network blip or a server error is not a client bug and must not take the launcher away.
- 2026-11-10 — M3-T1 — requests go through `frappe.call` with `silent: true` — the server messages of a background request would otherwise open a dialog over the user's work.
- 2026-11-10 — M3-T1 — the first summary is fetched 1 s after `app_ready` — the desk's own first requests go first, and the boot never waits on this app (NFR-PERF-02).
- 2026-11-10 — M3-T1 — the launcher's pulse on new items waits for M4-T1 — "new items" is decided by the alert policy (§7.4), and a pulse on any count change made here would be replaced there.
- 2026-11-10 — M3-T1 — until the window exists (M3-T2), clicking the launcher toggles a small card with the window title and each visible source's count — the brief allows a placeholder, and this one makes the summary behind the launcher checkable.
